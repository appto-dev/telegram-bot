# 3. Как устроена разработка бота

## 3.1 Один бот — один класс

Бот — наследник абстрактного класса `Bot`. Единственный обязательный метод — `boot()`: в нём и
только в нём регистрируется всё, что бот умеет.

```php
namespace App\ShopBot;

use Appto\TelegramBot\Bot\Bot;

class ShopBot extends Bot
{
    protected function boot(): void
    {
        // регистрация команд, кнопок, текстовых триггеров, middleware
    }
}
```

Сам класс `Bot` не должен разрастаться бизнес-логикой — если в `boot()` начинают появляться
`if`/`match` с логикой ответа, это сигнал вынести её в отдельный класс-хендлер.

## 3.2 Правило «одна задача — один класс»

Каждая единица поведения — отдельный небольшой класс:

| Что | Интерфейс | Куда класть |
|---|---|---|
| Команда (`/start`) | `CommandHandler` | `Commands/` |
| Callback-кнопка | `CallbackHandler` | `Callbacks/` |
| Многошаговый сценарий | `Dialog` (abstract) | `Dialogs/<Сценарий>/` |
| Один шаг диалога | `Step` | `Dialogs/<Сценарий>/Steps/` |
| Разметка клавиатуры | — (обычный класс) | `Keyboards/` |
| Промежуточная проверка | `UpdateMiddleware` | `Middleware/` |

Такая раскладка — не требование фреймворка (он не проверяет, где лежат файлы), а рекомендованная
конвенция, которой следует пакет-пример `app/MyBot`. Она окупается тем, что `boot()` бота
остаётся коротким и читаемым, а каждый класс тестируется независимо.

## 3.3 Путь одного апдейта простыми словами

1. Пришло новое сообщение/нажатие кнопки от Telegram.
2. Если у пользователя в этом чате уже идёт диалог (он на середине пошагового сценария) —
   апдейт уходит текущему шагу этого диалога, минуя всё остальное. Исключение — если пользователь
   ввёл команду (например, `/cancel` или любую другую): тогда диалог автоматически отменяется, а
   апдейт идёт дальше как обычно.
3. Иначе фреймворк по очереди проверяет: это команда? совпадает ли текст с зарегистрированным
   callback-паттерном? совпадает ли текст дословно с одним из `onText()`? подходит ли тип апдейта
   под `onUpdate()`?
4. Как только находится совпадение — выполняется ваш класс, и обработка апдейта на этом
   заканчивается.
5. Если ничего не подошло — вызывается необязательный `fallback()` бота (по умолчанию ничего не
   делает).

## 3.4 Что использовать: команда, кнопка или диалог?

| Сценарий | Инструмент |
|---|---|
| Разовое действие без ввода данных (`/start`, `/help`, показать баланс) | Команда (`onCommand`) |
| Реакция на нажатие инлайн-кнопки в уже отправленном сообщении | Callback (`onCallback`) |
| Реакция на нажатие reply-кнопки (кнопка под полем ввода) | Текстовый триггер (`onText`) |
| Нужно последовательно спросить несколько вещей (имя → email → подтверждение) | Диалог |
| Обработать «сырой» тип апдейта, для которого нет готового способа (например, `poll_answer`) | `onUpdate()` |

Если сомневаетесь между «одна команда с параметром» и «диалог» — ориентир простой: диалог нужен,
когда ответ пользователя должен запомниться *между сообщениями*. Если всё уместилось в одно
сообщение (команда с аргументами, кнопка с `callback_data`) — диалог не нужен.

## 3.5 Рекомендуемая структура папок

На примере `app/MyBot`:

```
app/ShopBot/
├── ShopBot.php              — сам бот, только boot()
├── Commands/
│   ├── StartCommand.php
│   └── CabinetCommand.php
├── Keyboards/
│   └── GlobalReplyMarkup.php
├── Middleware/
│   └── CaptchaMiddleware.php
└── Dialogs/
    └── Registration/
        ├── RegistrationDialog.php
        └── Steps/
            ├── AskName.php
            ├── AskEmail.php
            └── AskGender.php
```

Для нескольких ботов в одном приложении — отдельная папка на каждого (`app/MyBot`, `app/SupportBot`,
…), без общих классов-хендлеров между ними: у разных ботов обычно разная бизнес-логика, даже если
сценарий называется похоже.

## 3.6 Философия ответов пользователю

Внутри хендлера/шага у вас есть объект контекста апдейта, через который можно ответить без
ручного указания `chat_id` — фреймворк сам знает, кому и в какой чат отвечать:

```php
public function handle(UpdateContext $context): void
{
    $context->reply('Готово!');
}
```

Это осознанное решение: `chat_id`, а для business-сообщений ещё и `business_connection_id`,
подтягиваются из текущего апдейта автоматически — вручную их передавать почти никогда не нужно.
Подробнее — в [9. Ответы пользователю](09-replies.md).
